# AcousticLens 核心产品需求文档（PRD）

版本：v0.5  
状态：M4 真双麦宽带实时方向估计  
项目代号：AcousticLens  
一句话定义：用普通 Android 手机的真实双物理麦克风、摄像头和惯性姿态传感器，实时估计主要宽带声源的水平角度，并通过旋转累积显示方向热点。

## 1. 项目愿景

AcousticLens 让用户打开手机 App，对准一个持续发声的设备，在原地缓慢转动手机，在摄像头画面上看到指定频率声音的大致方向。

项目首先是一个可验证的声学研究与工程原型，其次才是一个面向大众的 App。最终目标不是“画出看起来像热力图的结果”，而是建立一条可复现、可测量、可解释的数据链路：

```text
双通道能力检测 → 音频与 IMU 姿态同步 → 旋转扫描 → 方向似然累积 → 热点叠加
```

## 2. 产品定位

### 2.1 目标用户

- 项目作者：声学研究生，理解声学、信号处理和阵列原理，但 Android 工程经验有限。
- 技术面试官：关注物理建模、实验设计、DSP、移动端工程和误差分析。
- 普通体验者：使用兼容的 Android 手机，对风扇、电机、扬声器等稳定声源进行探索。

### 2.2 核心价值

- 用纯手机路线降低体验门槛。
- 将声学、阵列信号处理、计算机视觉和移动传感器融合到一个可展示系统中。
- 保留原始数据和离线 Python 分析能力，使每个结果都可以复核。
- 用实验指标证明能力，而不是只展示视觉效果。

### 2.3 明确边界

第一阶段不承诺：

- 等价替代同步多麦克风阵列；
- 对拍手、语音等快速变化声源进行可靠定位；
- 支持所有 Android 手机；
- 实时完成复杂的 MVDR、MUSIC 或多声源分离；
- 通过深度学习“猜测”声源位置。

旋转扫描要求声源在扫描期间近似稳定，并且手机必须提供两个真正独立、同步的输入声道。若设备只返回单声道或复制声道，系统必须明确报告硬件能力不足，不能伪造声源定位结果。

## 3. 产品形态

### 3.1 V1：实验记录器

App 可以同时记录：

- 麦克风 PCM 音频及其时间戳；
- CameraX 预览；
- Rotation Vector、陀螺仪和线性加速度及其时间戳；
- 设备、采样率、音频源和配置元数据。

录制结束后生成一个可导出的 session，供 Python 离线分析。

### 3.2 V2：离线声学成像

用户选择目标频率，Python 工具读取 session，完成：

- STFT 和目标频率提取；
- 双通道独立性、互相关和时延检查；
- 音频与 IMU 姿态时间对齐；
- 不同朝向下的方向似然累积；
- 方位热力图和角度误差计算。

### 3.3 V3：App 内可视化

在手机画面中叠加指定频率的半透明热力图，并显示扫描质量、轨迹覆盖率和结果可信度。

### 3.4 V4：专业扩展

后续可选支持外部 Wi-Fi 麦克风阵列、实时处理、更复杂的阵列算法和 iOS。它们不属于第一阶段交付范围。

### 3.5 真双麦路由、设备几何与普通定位

Android 返回双声道不等于同时启用了两颗物理麦克风。目标设备实验证明 `VOICE_RECOGNITION` 只启用一颗物理麦克风后仍可返回处理双声道，而 `CAMCORDER` 会同时启用 `bottom` 与 `back` 两颗物理麦克风。App 必须在每次采集时记录 `AudioRecord.getActiveMicrophones()`；没有两颗活动物理麦克风时不得输出定位结果。

目标设备通过 Android 麦克风坐标报告的物理基线为 14.2567 cm。三方向宽带实验得到充电口侧 −21.64 samples、镜头前方约 +2.87 samples、充电口对侧 +21.88 samples，确认宽带 TDOA 的零点、符号和对称性。横屏且充电口朝右时，负 GCC 时延表示声源偏向屏幕右侧，正时延表示声源偏向屏幕左侧。

普通定位模式必须直接面对未知持续声源开始工作，不再要求声源预先位于镜头中央，也不再以 550.78125 Hz 单频拟合有效基线。550 Hz 文件与旧拟合模块只保留为历史实验和硬件诊断，不参与正式定位门禁。

实时定位统一采用横屏、充电口朝右。单帧方向由 500 Hz–8 kHz 宽带 GCC-PHAT 时延和固定物理基线换算，经过物理范围检查、峰值质量、双声道差异和时间中位数平滑后输出角度与置信度。IMU 旋转轨迹用于后续解决前后歧义和累积方向概率图。

## 4. 技术原则

1. 先采集和验证数据，再实现算法，再做实时 UI。
2. 所有关键声学算法先用 Python 验证，再考虑 Android 移植。
3. 优先采用经典 DSP、几何和阵列信号处理，不引入无必要的神经网络。
4. 任何依赖手机型号的能力都必须在运行时检测并记录。
5. 所有重要结果必须有可重复实验、误差指标和失败条件。
6. Agent 可以生成代码，但不能替代对声学模型、坐标系、时间同步和实验结果的解释。

## 5. 系统架构

```text
Android App
├── Audio Capture       AudioRecord 起步，评估 Oboe/AAudio
├── Camera Preview      CameraX
├── Orientation         Rotation Vector + Gyroscope；不依赖 ARCore
├── Synchronization     统一 monotonic 时间轴、插值、漂移检查
├── Session Storage      WAV + CSV + JSON + 可选视频
└── Export              ZIP/session 目录导出

Python Offline
├── io.py               读取 session 和元数据
├── spectrum.py         FFT、STFT、频谱分析
├── orientation.py      姿态、角速度和角覆盖检查
├── sync_check.py       音频/IMU 对齐与时钟分析
├── simulation/         双麦克风、声源方向和虚拟旋转仿真
├── direction.py        TDOA/相位差与方向似然累积
└── experiments/        误差、频率、孔径、重复性分析
```

## 6. 数据格式要求

每次录制保存为：

```text
sessions/YYYY-MM-DD_HHMMSS/
├── audio.wav
├── acoustic_features.csv
├── orientation.csv
├── metadata.json
├── events.csv
└── optional_video.mp4
```

`orientation.csv` 至少包含：

```text
sensor_timestamp_ns,callback_monotonic_ns,qx,qy,qz,qw,yaw_deg,pitch_deg,roll_deg,yaw_span_deg,angular_speed_rad_s,linear_acceleration_m_s2
```

`acoustic_features.csv` 保存与音频帧编号绑定的 GCC-PHAT 时延、峰值比、双声道差异、实时宽带角度、方向置信度、质量状态，以及约 550–1150 Hz 的诊断性多频段互谱相位和幅度。

已知方向扫描只用于开发者为每个受支持设备型号建立一次设备配置，不属于普通用户工作流。正常定位模式面对未知声源直接旋转扫描，读取已保存的设备配置并输出方向估计；不得要求用户先把未知声源放在准星中央。

`metadata.json` 至少包含：

```text
device_model
android_version
app_version
sample_rate
channel_count
audio_encoding
audio_source
agc_enabled
noise_suppression_enabled
echo_cancellation_enabled
camera_intrinsics
microphone_assumed_position
coordinate_convention
session_start_time
notes
```

所有时间戳必须明确单位、时钟来源和转换方法，禁止只保存一个无法解释的系统时间。

## 7. 分阶段路线图

### Milestone 0：技术方案与风险基线

目标：明确 Android 技术栈、数据协议、坐标系、时间轴和实验方案。

交付物：

- `README.md`、`docs/architecture.md`、`docs/timestamps.md`；
- 项目目录和构建说明；
- 设备兼容性检查表；
- Python 环境和最小测试框架；
- 风险清单及验证顺序。

验收：不写大规模业务代码，也能说明每个模块输入、输出和验证方法。

### Milestone 1：Android 采集骨架

目标：在至少一台 Android 设备上稳定记录优先立体声音频、摄像头预览和 IMU 姿态。

验收：录制 30 秒 session；WAV 可播放；orientation.csv 连续；界面显示通道数、时延、姿态、角覆盖和录制状态；导出文件可在电脑读取。必须判定两个声道是否独立。

### Milestone 2：Python 数据检查工具

目标：独立检查音频质量、双通道独立性、姿态质量、时间戳质量和设备方向标定质量。

验收：可以绘制 waveform、spectrogram、摄像头前向角和相位随旋转变化；报告采样间隔、角速度、掉帧、通道差异、可靠频段、有效基线和摄像头—麦克风轴向偏置。

### Milestone 3：双麦旋转扫描仿真

目标：在不依赖手机的情况下证明几何模型和算法方向正确。

内容：点声源、单频/宽带信号、已知双麦间距、旋转姿态、传播时延、白噪声、不同基线和频率。

验收：方向似然峰值接近真实声源；输出角度误差、主瓣宽度和置信度；测试能解释频率、麦克风基线和 SNR 的影响。

### Milestone 4：真双麦宽带实时方向实验

目标：用宽带测试噪声和持续语音验证实时水平角度、置信度与失败拒绝。

验收：完成 −60°、−30°、0°、+30°、+60° 五角度实验及至少两轮重复；左右方向全部正确，1 m安静环境平均误差不超过 10°–15°；低质量窗口必须拒绝或降低置信度，不能输出无依据角度。

### Milestone 5：结果可视化

目标：将离线成像结果叠加到相机画面，并展示扫描质量。

验收：用户可以选择频率；界面显示轨迹覆盖率、扫描速度、追踪状态和结果置信提示；无法满足假设时给出警告，而不是输出无解释的热图。

### Milestone 6：产品化实验版本

目标：形成可公开演示和放入作品集的 Android APK、GitHub 项目和实验报告。

验收：新用户按照 README 能完成安装、录制、导出和查看结果；至少有一段演示视频、仿真图、真实实验图和误差统计。

## 8. 最小可行实验

实验对象：固定位置的扬声器。  
信号：500 Hz–8 kHz宽带噪声，随后增加持续语音。  
距离：约 1 m。  
扫描：手机位置尽量不变，绕竖直方向缓慢左右旋转，总角覆盖约 60°。  
输出：方向热力图和真实/估计方位角误差。

实验必须同时保留：

- 原始 WAV；
- 完整 orientation.csv；
- 手机姿态和扫描方向；
- 目标频率、扫描平面和声速假设；
- 失败原因和人工观察。

## 9. 评价指标

项目不能只用“热力图看起来对”作为结论。至少记录：

- 定位误差：cm；
- 角度误差：deg；
- 主瓣宽度；
- 峰值与旁瓣比；
- 扫描轨迹覆盖率；
- 位姿丢失率；
- 音频有效帧比例；
- 重复实验的 mean、std 和最大误差；
- 结果对频率、孔径、距离和 SNR 的敏感性。

## 10. 主要风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 手机音频被 AGC/降噪处理 | 破坏幅相一致性 | 运行时检测、记录配置，优先使用可关闭处理的设备 |
| 设备只提供单声道或复制声道 | 无法利用内置麦克风时差定位 | 立体声优先申请，记录通道差异；不满足即明确停止该路线 |
| 音频与 IMU 时钟不一致 | 声学约束映射到错误朝向 | 统一 monotonic 时间轴，估计 offset 和 drift |
| IMU 航向漂移或磁干扰 | 热点角度偏移 | 使用 Game Rotation Vector、短时扫描和回到起点检查 |
| 手机麦克风位置未知 | TDOA 到角度映射存在系统误差 | 先做时延随旋转的经验标定，再建立设备配置 |
| 手机移动产生摩擦/风噪 | 污染音频 | 运动提示、质量评分、频段筛选和实验规范 |
| 设备兼容性差 | 无法复现 | 首先支持有限设备清单，启动时显示能力检查 |

## 11. 暂不实现的功能

以下内容只进入 roadmap，不得提前扩大第一阶段范围：

- SRP-PHAT、MVDR、MUSIC；
- 多声源同时成像；
- 语音、拍手等瞬态声源定位；
- 深度学习定位；
- 外部 Wi-Fi/BLE 阵列；
- 实时 GPU 波束形成；
- 自动频率选择；
- iOS 版本；
- 高精度麦克风指向性和外参标定。

## 12. 开发与变更规则

每个 Milestone 必须完成：

1. 明确输入、输出和验收标准；
2. 实现最小范围代码；
3. 运行测试或真实实验；
4. 记录结果和已知限制；
5. 更新 README、docs 和实验记录；
6. 再进入下一个 Milestone。

任何新功能如果不能说明它服务于哪个 Milestone，暂不加入主线。任何算法结果如果没有原始数据、参数和误差指标，不视为完成。

## 13. 项目最终完成定义

AcousticLens 达到第一版完成标准时，应满足：

> 使用一台兼容的普通 Android 手机，能够采集双通道音频和 IMU 姿态；能够导出可复核的 session；能够在 Python 中完成时间对齐、通道时延估计和旋转方向似然累积；在稳定已知声源实验中得到具有重复性的方向热图，并清楚说明误差、适用条件和失败条件。

这份 PRD 是项目基线。后续开发优先服从其中的阶段目标和验收标准；如果技术事实证明某项假设不成立，应更新 PRD 并记录原因，而不是用未经验证的代码掩盖问题。
